# I2 — c=2 Tax Audit

**Scope:** every `start_cluster.sh` knob whose own comment justifies a c=1 throughput/latency
cost in exchange for c>=2 stability or correctness. Audit only — no knobs changed, no relaunch,
no traffic sent to the cluster.

**Background:** the user formally dropped c>=2 concurrency on 2026-09-01 ("workload shape
doesn't fit c=2+"). Production `start_cluster.sh` still carries every knob below at its
c>=2-favoring value. This table enumerates that tax as documented **in the script's own
comments** — none of the cost/benefit numbers below are measurements taken during this audit.

## Interaction constraint verification: `MLX_STEEL_BATCH_INVARIANT=0` requires `EXO_DSV4_VERIFY_ROWSEQ_VEC=0`?

start_cluster.sh:259 states: "The ~5% c=1 decode cost noted above is absorbed by the vec win (33.7 vs 29.5 net). Set =0 only with EXO_DSV4_VERIFY_ROWSEQ_VEC=0."

Code trace:
- `_RowseqVecMixin.rowseq_vec` docstring at mlx-lm/mlx_lm/models/deepseek_v4.py:6011-6023 states the vectorized per-row fold path "REQUIRES MLX_STEEL_BATCH_INVARIANT=1 for per-row bitexactness of the batched call vs the sequential S=1 call."
- `rowseq_vec_supported()` (deepseek_v4.py:6028-6029) gates on `_VERIFY_ROWSEQ_VEC and _rowseq_vec_ring_ok(cache)` — it does **not** check `MLX_STEEL_BATCH_INVARIANT` at all.
- `_VERIFY_ROWSEQ_VEC` is set from `EXO_DSV4_VERIFY_ROWSEQ_VEC` at module import (deepseek_v4.py:5587).
- `steel_batch_invariant_enabled()` (matmul.cpp:108-112) is an independent, unrelated static bool with no cross-reference to any DSv4/rowseq state.

**Verdict: the constraint is a documentation/comment-only requirement, NOT code-enforced.** Nothing in the current source checks or asserts that `EXO_DSV4_VERIFY_ROWSEQ_VEC=0` whenever `MLX_STEEL_BATCH_INVARIANT=0` is set (or vice versa). Setting `MLX_STEEL_BATCH_INVARIANT=0` while leaving `EXO_DSV4_VERIFY_ROWSEQ_VEC=1` (the current production default per start_cluster.sh:1928) would silently violate the "REQUIRES ... for per-row bitexactness" contract documented at deepseek_v4.py:6022 with no runtime guard catching the misconfiguration — a real correctness footgun if row 2 is ever flipped without also flipping `EXO_DSV4_VERIFY_ROWSEQ_VEC`.

## TOTAL DOCUMENTED TAX

**These are the comments' own claims, not measurements taken during this audit.** No cluster requests were sent; no benchmarks were run.

- **Decode throughput tax (c=1):**
  - `EXO_DSV4_FENCE_EVERY_N_LAYERS=4` vs `=8`: **~0.7 t/s** (29.7 → ~29.0, start_cluster.sh:468-469)
  - `MLX_STEEL_BATCH_INVARIANT=1` vs `=0`: **~5% decode** (start_cluster.sh:252, 258)
  - `EXO_DSV4_FUSED_MOE`/`COMPILE_FFN`/`COMPILE_LAYER` combined: **~3-4%** (start_cluster.sh:426-428) — **but this wiring is confirmed removed from the code (Discrepancy D1), so this cost is not actually being paid today regardless of the env values.**
  - `MLX_GEMV_BATCH_INVARIANT=1` vs `=0`: **no documented c=1 % figure** (Discrepancy D2) — cannot be summed.
  - `EXO_DSV4_SPEC_CACHE_ROLLBACK_C2`: no c=1 cost documented (it's a c=2-only lever, Discrepancy D3) — not includable in a c=1 tax sum.
  - `EXO_DSV4_MTP_C2_MAX_CTX`: no c=1 cost documented; the gate it used to drive is dormant (Discrepancy D4) — not includable.
  - `EXO_MAX_ACTIVE_TASKS`: no c=1 cost documented at all; not a concurrency knob per its own comment (Discrepancy D5) — not includable.

  **Sum of figures that are both (a) genuinely quoted as a c=1 cost and (b) currently live in the code path:**
  **~0.7 t/s (fence cadence) + ~5% decode (steel batch invariance) ≈ 0.7 t/s + 5% — these are not directly additive (one is absolute t/s, one is %) and are measured against different baselines (29.7 t/s vs 29.5 t/s), so report separately rather than combined into one number.** The `~3-4%` FUSED_MOE/COMPILE_* figure is EXCLUDED from any live total because the wiring is removed (D1).

- **TTFT tax (c=1):**
  - `EXO_BATCHED_PREFILL_RENDEZVOUS_MS=200` vs `=0`: **200ms added to every c=1 first-token** (start_cluster.sh:131-132, constants.py:133). This is the only TTFT-specific tax documented across all ten rows.

**Bottom line:** the two knobs with unambiguous, code-live, quoted c=1 costs are `EXO_DSV4_FENCE_EVERY_N_LAYERS` (~0.7 t/s decode) and `MLX_STEEL_BATCH_INVARIANT` (~5% decode), plus `EXO_BATCHED_PREFILL_RENDEZVOUS_MS` (200ms TTFT). The remaining five/six knobs in the starting list either have no live code path (D1), no quoted c=1 percentage (D2), are pure c=2 levers with zero c=1 cost (D3, D8), have an internally-contradicted/dormant gate (D4), or aren't concurrency knobs at all per their own comment (D5).

## DISCREPANCIES

- **D1 — `EXO_DSV4_FUSED_MOE` / `EXO_DSV4_COMPILE_FFN` / `EXO_DSV4_COMPILE_LAYER` wiring is removed, not just defaulted off.** start_cluster.sh sets all three to `0` (lines 434-436) and its comment (420-433) frames them as live, settable levers ("set any of these =1 to re-enable for single-stream-only experiments"). But `src/exo/worker/engines/mlx/auto_parallel.py:110-118` states outright: "DSv4 MoE/layer FUSION + mx.compile paths — REMOVED 2026-06-18. ... Combined they bought only ~3-4% throughput, so the wiring is removed entirely (not just defaulted off) to guarantee fusion can never install. The fused/compiled method bodies in mlx-lm deepseek_v4.py are likewise removed." A repo-wide grep for `os.environ`/`getenv` reads of these three variable names found **zero** references in `src/exo/` or `mlx-lm/mlx_lm/` (only in `bench/` harness scripts and the `build/` mirror of the source, which is a stale copy, not the live code path). **The env vars in start_cluster.sh are currently no-ops** — setting them to `1` would not re-enable anything, contrary to what the comment at start_cluster.sh:429-430 implies ("set any of these =1 to re-enable"). This should be flagged to the user/PM: the comment is stale relative to the code, and the "c=2 tax" these three lines appear to represent in start_cluster.sh is not actually being paid or avoidable via env var today.

- **D2 — `MLX_GEMV_BATCH_INVARIANT` has no quoted c=1 cost figure**, unlike its sibling `MLX_STEEL_BATCH_INVARIANT` two lines below it. The comment block at start_cluster.sh:250-255 covers both flags together but the ~5% number explicitly attaches to steel batch invariance only ("costs ~5% c=1 decode" at line 252, in a sentence about steel-level batch invariance specifically). matmul.cpp's own comment (lines 86-92) documents *what* GEMV_BATCH_INVARIANT does mechanically but likewise quotes no throughput delta. It cannot be summed into "total documented c=2 tax" without a number; flagging that this knob's c=1 cost is asserted implicitly (by grouping) but not quantified anywhere in the source.

- **D3 — `EXO_DSV4_SPEC_CACHE_ROLLBACK_C2` is not a c=1-cost-for-c=2-benefit knob at all.** Its entire documented cost/benefit trade (dsv4_mtp.py:721-724) is c=2-vs-c=2 (a cheaper c=2 rollback path vs. a more expensive c=2 rollback path); it says nothing about c=1 behavior, and the code paths it touches are gated on batch size >= 2 (dsv4_mtp.py:2672, 2692, 3145). It does not belong in a "c=1 tax" audit on the comment evidence found — included in the table per the task's explicit starting list, but flagged here as not matching the audit's own inclusion criterion.

- **D4 — `EXO_DSV4_MTP_C2_MAX_CTX`'s local comment (start_cluster.sh:1994) is stale relative to the code it drives.** The line-1994 comment still describes the flag as a live binary "spec-off at c>=2 (default) / spec on" switch, matching the flag's *original* design from the historical block at start_cluster.sh:1969-1993. But the actual consuming code (dsv4_mtp.py:2371-2380) explicitly documents that this gate was **removed 2026-06-24** because its root cause (a ring-bootstrap positioning bug) was fixed elsewhere, and states plainly: "The env var is still read for backward-compat safety but no longer has a default-threshold effect" when set to its default value of `1`/`0`-as-"no gate" semantics — i.e. `_c2_max == 0` is now the no-op branch, and the *actual* production value of this var (`1`, per start_cluster.sh:1994) does **not** correspond to "spec-off at c>=2" in the current code; it corresponds to "gate active with threshold=1" per the `else` branch at dsv4_mtp.py:2380-2385, which behaves differently than the start_cluster.sh comment claims. This is a live discrepancy between the launch script's own comment and the code's actual current semantics and should be re-verified by someone with runtime access before being relied on for a future c=1-recovery decision.

- **D5 — `EXO_MAX_ACTIVE_TASKS` does not belong in a c=1-cost-for-c>=2-benefit audit at all**, on the evidence in start_cluster.sh and transforms.cpp. Its documented rationale (start_cluster.sh:10-15, transforms.cpp:26-32) is exclusively about GPU command-buffer queue depth vs. a macOS WindowServer watchdog crash — a stability concern orthogonal to request concurrency count. Nothing in either comment frames the value 5-vs-10 as a c=1-throughput-vs-c>=2-stability trade; it reads as a general anti-crash safety margin that would apply identically at c=1. Included in the table because it was in the task's starting list, but flagged as likely mis-categorized — testing/reverting it in a future round should not be billed against "c=2 tax recovery."

- **D6 — `EXO_DSV4_SPEC_CACHE_ROLLBACK_C2` and `EXO_DSV4_MTP_C2_MAX_CTX` module-level reads mean env-var edits to these two require a full runner relaunch even though `EXO_DSV4_MTP_C2_MAX_CTX`'s OTHER read site (dsv4_mtp.py:2378, inside `_next()`) is per-cycle.** `_SPEC_CACHE_ROLLBACK_C2` (row 8) is a true module-level constant baked in at import — only one read site, unambiguous relaunch requirement. `EXO_DSV4_MTP_C2_MAX_CTX` (row 9) has exactly one read site and it IS inside the per-cycle `_next()` method (not a module-level constant), so it is genuinely runtime-re-readable within a live process if the process's own environment is mutated — but start_cluster.sh's allowlist mechanism (per the task background, ~lines 1620/2037/2100/2456) controls what reaches the runner process's env at spawn time, so in practice testing a new value still means restarting the runner via start_cluster.sh even though the Python-level read is per-cycle. Flagging this nuance so a future round doesn't assume "runtime-settable" means "no relaunch needed in this deployment."
