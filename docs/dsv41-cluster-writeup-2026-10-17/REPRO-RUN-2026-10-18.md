# Reproduction run — 2026-10-18 (author-executed)

A dated record of executing **§11 "How to reproduce" end to end** at the SHA §11 pins,
`b88d65dd3304`. It is appended evidence, not a rewrite: nothing in §9 is replaced by it,
and where a §9 figure did not reproduce, the discrepancy is stated rather than smoothed.

**Who ran it.** The owner (author of the writeup), not a third party. Fable's review asked
for this distinction by name: an author-executed run is worth doing, but it is not
third-party verification, and it should be labelled that way.

**Verdict in one paragraph.** The pinned SHA boots on the hardware, the instance comes up
with every constant §11.4 expects, and the §11.5 depth rows reproduce the §9.2 prefill
figures within 0.7–6.7% and the decode figures within 0.2–6.3% on five of six rows — with
cache states that match the writeup's own on the four shallow rows. The exception is 300K
decode, measured ~4× faster than §9.2 claims (below). §11.7's guard and limiter repros both
behave as documented. The **1M row did not complete**: it failed at dispatch when sent
through the non-master node, and on the master node it wedged the jaccl transport on the
first large collective and was SIGKILLed by the hang watchdog at ~70 s, twice on two
different boots. That is the one §11 step this run cannot mark as reproduced.

**The 300K decode discrepancy is real and is the most important number in this record.**
§9.2 reports 5.9/6.0 tok/s at 300K (the "cliff"); this run measured 21.86/22.12 tok/s on the
first boot and 24.92/25.25 tok/s on a second boot with the whole 300K prefix restored from
the park store. Both channels agree each time. So at the SHA §11 pins, 300K decode is
~4× faster than §9.2's figure. §9 was measured at `5a18b81`/`991cf11`, not at `b88d65dd`;
this run cannot say which of those commits (or which boot state) explains the difference —
that is an open question, recorded rather than resolved. It also means §10.1's "two cliffs"
framing should not be quoted against `b88d65dd` without re-measuring.

### Cache state caveat (why two rows are not like-for-like)

The writeup's 160K and 300K rows both had `cached_tokens = 0` (cold prefill). This run's
sequential pass left a resident prefix for each of those rows (`98,304` and `159,744`
cached), so their uncached rates are rates over the *deeper* part of the prompt, not the
whole prompt. I tried to re-create the cold condition by relaunching the pinned SHA and
re-running 300K as the first request. It came back `cached = 300,003`, `prefill = 0.00 s`:
the engine's park store restores prefix snapshots across a full process restart, so a
relaunch alone cannot produce a cold prefill. A genuinely cold 160K/300K (or 1M) row needs
the park store cleared first — a state change on the nodes that this run did not make.

Generated text (the needle question, answers truncated to 200 chars) — the figures above are
read against real output, not just token counts:

- 10K: "BOTTLENECK: … the MoE `switch_mlp` / quantized GEMV path in DSv4 prefill — the expert-routing matmul that dominates chunk wall time…"
- 100K: "BOTTLENECK: … the `moe.all_sum` cross-rank collective in the MoE forward pass — it appears in at least 20 distinct documents spanning 2026-05-14 through 2026-08-22…"
- 300K: "BOTTLENECK: … the **`moe.all_sum` cross-rank collective** — the per-layer MoE partial-sum reduction that runs on jaccl's CPU stream and forces a GPU→CPU→GPU drain every layer…"

## §11.8 — 300K decode A/B across the two SHAs (cold): no SHA effect

Two boots, park store emptied before each (0 entries on both nodes; both rows report
`cached = 0` client-side and `reuse: 0` server-side), one 300K row each, same body
(`prompts/depth_d300k.json`), master API, temperature 0:

| SHA | prompt | cached | prefill s (server) | prefill tok/s | client dec | server dec | wall s |
|---|---|---|---|---|---|---|---|
| `5a18b81` | 300,003 | 0 | 1419.54 | 211.3 | 13.82 | 13.89 | 1434.52 |
| `b88d65dd` | 300,003 | 0 | 1418.51 | 211.5 | 13.87 | 13.94 | 1433.51 |

The two SHAs agree to 0.2% on every channel. So the 21.86/22.12 and 24.92/25.25 tok/s recorded
earlier in this run were **not** a fix between the SHAs. At one fixed SHA (`b88d65dd`) the same
row measures 13.9 cold, 22.1 with 159,744 tokens restored from the park, and 25.2 with the full
300,003 restored: decode rate at 300K is a function of how much of the prefix is already
resident, not of the code and not of the depth alone.

Round structure, same method as §9.2's table (tokens per speculative round, median gap):

| SHA / state | tokens/round | median inter-round gap | implied tok/s |
|---|---|---|---|
| `5a18b81`, cold | 2.73 | 0.197 s | 13.9 |
| `b88d65dd`, cold | 2.73 | 0.195 s | 13.9 |
| `b88d65dd`, 159,744 restored | — | — | 22.1 |
| §9.2 claim (`5a18b81`, `cached 0`) | 2.9 | 0.486 s | 6.0 |

Round size is unchanged across both SHAs; the whole difference is per-round cost (0.196 s today
vs 0.486 s claimed) — exactly the variable §9.2 itself names as "a per-round cost of
unidentified origin (residency / spill is a named candidate, not proven)". This run promotes
residency from candidate to survivor: three cache states, one build, a 1.8x swing in round cost.

**What still does not tie out.** §9.2's 0.486 s round cost at 300K, on the same code lineage and
the same `cached = 0` condition, against 0.196 s today. Prefill on that row matches (+8.2% on
195.4 tok/s) and the rest of §9.2 reproduces within 0.7–6.7%, so the machine was not globally
slow that night. Two candidates remain, recorded rather than guessed:

1. concurrent traffic on the same instance — §9.2 itself notes five further points "harvested
   from another client's traffic on the same build and instance";
2. machine thermal / fan state at 02:31 vs 18:20 (fans are script-managed, §8.1).

Next attack vector, and the only one reproducible on demand: re-run 300K while a second client
streams on the instance and compare the round gap.

**Why `5a18b81` is the right comparison for §9.2:** the 300K row ran at 02:31, before the
10:05–10:12 deploy of `991cf11` (§12.4), so it was taken on plain `5a18b81`. `991cf11` adds a
per-round liveness beat and an output cap (8192 default); this row used `max_tokens 200`, so
neither can move decode rate — and `b88d65dd`, which contains `991cf11`, measures the same as
`5a18b81` anyway.

## §11.9 — cold 1M row: never accepted, same as the warm attempts

Sixth attempt, this time deliberately cold: park store emptied before the boot (0 entries), sent
to the master's API, same `prompts_1m.json` (1,000,003 prompt tokens, `max_tokens 100`, temp 0,
stream on). Outcome: never accepted. The master logged `Sending overlarge payload, network
performance may be temporarily degraded` at 0 s, then `not accepted after 15s` / `not accepted
after 30s` / `Giving up … never accepted`; the client received the 500 error event at 55.2 s with
zero token frames. The cluster was healthy afterwards (1 instance, 2 runners `RunnerReady`,
0 tasks) — unlike the accepted attempts 3–4, which were SIGKILLed at ~70 s.

So the 1M failure is not park-state dependent. It is also **not** a size or placement refusal —
§11.11 rules both out with measurements (bodies up to 12 MB cross the node link and are accepted;
the master applies no length or placement check). What the master's log shows is that it never
received this command at all.

## §11.10 — Concurrency: a second chat request does not overlap a 300K decode

Setup: the 300K row re-sent on the same boot with a second streaming request fired from the same
process the instant the row's first content token was parsed (`contention2.py`). A first attempt
that triggered by polling the client's own `.sse` file fired ~5 s late — the file is buffered — and
produced only a clean baseline repeat (13.43 client / 13.62 server tok/s).

| quantity | value |
|---|---|
| 300K row | 194 frames, 71 rounds, 2.73 tok/round, median gap **0.201 s**, 13.58 tok/s |
| second request's TTFT | 15.13 s |
| round gaps overlapping the second stream | **0** |

The second request's first token arrived 15.1 s after it was sent — after the row's 14.28 s decode
had already ended — and not one round of the big row overlapped it. On this instance and build a
second chat request is **serialized** behind the first; it does not decode concurrently.

Consequence for §9.2: a concurrent *chat* client cannot explain that row's 0.486 s round cost, so
the "another client's traffic" note in §9.2 is not a live explanation for it on this build. With
code (A/B, identical), cache state (three states) and concurrency now ruled out, the remaining
candidate is a one-off residency/refault event on that turn — §10.1 already records refault as
CONFIRMED as a phenomenon — which no lever available today reproduces on demand. That is the honest
state: not explained, but narrowed to a state we cannot currently drive.

Method note for cold rows (§11.8): an empty park store is **not** sufficient by itself — the
instance's in-memory prefix cache survives between requests, so re-sending the same prompt on the
same boot returns `ttft 0.46 s` even with the park store empty. A cold row needs a fresh instance
or a fresh prompt; the §11.8 rows were taken on fresh boots and report `cached = 0`, so they stand.

## §11.11 — 1M delivery: payload size and the transport are ruled out up to 12 MB

The 1M body is 3,334,717 bytes. Bodies were sent to the **non-master** node's API, so the command
had to cross the node-to-node link to the elected master; prompt stays tiny, padding goes in `stop`:

| body bytes | outcome | secs |
|---|---|---|
| 899,995 | accepted | 1.48 |
| 1,031,706 (= the 300K row's body) | accepted | 0.48 |
| 1,199,995 | accepted | 0.40 |
| 1,599,995 | accepted | 0.33 |
| 2,199,995 | accepted | 0.47 |
| 3,334,712 (= the 1M body's size) | accepted | 0.51 |
| 3,999,995 / 5,999,995 / 7,999,995 / 11,999,995 | accepted | 0.57-0.81 |

The master's own log carries `Executing command: TextGeneration` for these, so they crossed the
link rather than completing locally.

In code, the master's command processor (`src/exo/master/main.py:340-405`) applies **no** length,
memory or placement check to a `TextGeneration`: if an instance for the model exists it appends
`TaskCreated` immediately. "Never accepted" therefore cannot be a placement refusal — it means the
command never reached the master's command processor.

That leaves the 1M *content*: a 1,000,003-token user message. The API published that command four
times (one `Sending overlarge payload` warning per publish, 18:28:19-18:29:14) and the master's log
for the window contains no trace of the command id, with no error on either node. A command is
built from the message **text** (`TextGenerationTaskParams.input`), not token ids, so it is ~the
body's size — inside the range proven above.

Two corrections to earlier text in this record follow: §11.9's "the master refuses the 3.3 MB
command too" — it never received it; §11.5's "the non-master path silently fails for >1 MB" — not
the discriminator, since every size above used the non-master node's API successfully.

Next step to close it: instrument publish and receive — one INFO line each with command id,
serialized size and a digest — redeploy, replay the 1M body. If the receive line appears the gap is
after receipt; if it does not, the loss is inside the API's publish path, which the warning proves
was entered but not that it delivered.

## Document discrepancies found by running it

1. **Shard count**: §1.3 and §11.1 say 40 safetensors shards; there are 39 (byte total is right).
2. **§11.5 says the prompt files and their generator "are not in this repo"**. At `main` they
   are: `scripts/gen-prompts.py` (deterministic, pinned SHA + tokenizer) and `prompts/`
   (committed). The bodies are equivalent-class reconstructions, not the originals — that
   caveat stays — but "bring your own" is no longer true.
3. **300K decode** (§9.2): resolved by §11.8. Cold, both SHAs agree at 13.9 tok/s (2.3x faster
   than the 5.9/6.0 claimed); the earlier 21.9–25.3 tok/s were cache-restored rows at the same
   SHA, not a code improvement. §9.2's 6.0 is the outlier at every cache state measured; the
   only unexplained part is its round cost, and a concurrent chat client is ruled out as the
   cause (§11.10 — decode is serialized on this build).
4. **Large-prompt dispatch** (§11.3–11.5): the "non-master API never accepts a >1 MB command"
   finding does not survive measurement (§11.11: 0.9–12 MB bodies are accepted from the
   non-master API). The 1M body specifically is published and never reaches the master — an
   unexplained delivery loss for that content, not a size or placement gate.
5. **Cold rows cannot be re-created by a relaunch**: the park store restores prefix snapshots
   across restarts (`cached = 300,003`, `prefill 0.00 s` after a clean boot), so §9.2's
   `cached = 0` rows for 160K/300K need the park store cleared first. §11.8/§11.9 did that
   (store moved aside, then restored). Parking is eviction-driven — a single-row boot leaves
   the store empty — and an empty store is *not sufficient*: the instance's in-memory prefix
   cache survives between requests, so a repeated prompt on the same boot is warm even with the
   park empty (§11.10). A cold row needs a fresh instance or a fresh prompt.

## What this run proves, and what it does not

Proves: the pinned SHA boots on this hardware; the hardcoded node/peer constants are
sufficient; §11.4's instance constants are exactly as documented; the depth-row and
guard/limiter figures reproduce within the deltas above; the 300K decode difference is a cache
residency effect and is SHA-independent; a second chat request does not overlap a 300K decode
(§11.10); payloads up to 12 MB cross the node link and are accepted (§11.11), so neither size
nor placement refusals explain the 1M; the 1M command is published and never reaches the master.

Does not prove: third-party independence (author-executed); that a warm or cold 1M can be made
to run at this SHA (no attempt has produced a token); why the 1M command is lost between publish
and the master (§11.11 names the instrumentation that would separate the two ends); why §9.2's
round cost was 2.5x today's — with code, cache state and concurrency each ruled out, the
surviving candidate is a one-off residency/refault event of the kind §10.1 already records.
